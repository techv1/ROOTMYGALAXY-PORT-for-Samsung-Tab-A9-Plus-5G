## 4. 推送与运行

```bash
# 推送二进制 + 完整性校验
adb -s 10AE8G1*** push ghostlock /data/local/tmp/ghostlock
adb -s 10AE8G1*** shell "chmod 755 /data/local/tmp/ghostlock; md5sum /data/local/tmp/ghostlock"

# observe 冒烟（不触发 PI walk）
adb -s 10AE8G1*** shell "cd /data/local/tmp && GHOSTLOCK_OBSERVE=1 GHOSTLOCK_ROUTE=mcast GHOSTLOCK_CORE=4 GHOSTLOCK_CONSUMER_CORE=5 timeout 90 ./ghostlock"

# 正式运行（失败会 panic 重启）
adb -s 10AE8G1*** shell "cd /data/local/tmp && GHOSTLOCK_ROUTE=mcast GHOSTLOCK_CORE=4 GHOSTLOCK_CONSUMER_CORE=5 ./ghostlock"
```

### 4.1 环境变量

| 变量 | 取值 | 作用 |
|------|------|------|
| `GHOSTLOCK_ROUTE` | `mcast` / `tcp` / `pselect` | 选择投毒 transport（本次新增 mcast；未设时按 `GHOSTLOCK_TCP_ROUTE` 与 `compact_waiter` 推断） |
| `GHOSTLOCK_MCAST_ROUTE` | `1` / `0` | `GHOSTLOCK_ROUTE` 未设时的 MCAST 开关 |
| `GHOSTLOCK_TCP_ROUTE` | `0` | 关闭 TCP 默认（选 pselect） |
| `GHOSTLOCK_OBSERVE` | `1` | 只投毒不触发 walk，用于安全冒烟 |
| `GHOSTLOCK_CORE` / `GHOSTLOCK_CONSUMER_CORE` | 整数 | 主线程 / consumer 绑核（建议 4 / 5） |
| `GHOSTLOCK_HOME` | 路径 | offsets/日志目录（默认 `/data/local/tmp`） |
| `GHOSTLOCK_KSU_LOG` | 路径 | root 脚本日志路径（默认 `<home>/.ghostlock_ksu.log`） |
| `GHOSTLOCK_DISABLE_MODULES` | `1` | root 脚本加载 KernelSU 前禁用全部模块（安全模式） |

## 5. 日志与取证

### 5.1 运行日志

- 程序输出为 stdout（ANSI 颜色），PC 端建议 `Tee-Object` 落盘。
- **缓冲陷阱**：stdout 为管道时是块缓冲；进程不退出时，`TIMER()`/`log_sync()` 之后的行可能长期不落盘（本次成功日志即截断在 “PI route done”）。需要完整日志时优先拉取设备侧文件：

```bash
adb -s 10AE8G1*** pull /data/local/tmp/.ghostlock_ksu.log D:\daima\tmpbuild\ksu_log_latest.log
```

- PowerShell 直接 `>` 重定向会写成 UTF-16；用 `Tee-Object` / `Out-File -Encoding utf8`，或读文件时按 `utf-16` 解析。

### 5.2 root 脚本日志（uid=0 后）

`/data/local/tmp/.ghostlock_ksu.log`：包含 `root script start uid=0`、`policy fixup rc`、`late-load` 结果与 `[+] KernelSU module loaded`。

### 5.3 panic 现场

- panic 后设备自动重启；`/sys/fs/pstore` **仅在重启后首次开机可读**，尽快拉取。
- 既有现场：`D:\daima\tmpbuild\ramoops_p2..p8_preinit.txt`（8 次同签名 crash）。
- 关键寄存器读法（示例，panic #8）：`x19`=task、`x26`=x19+0x924、`x25`=waiter、`x24`=waiter->lock、`x0`=trylock 参数。

### 5.4 dmesg 限制

shell 上下文 `dmesg` 常被 SELinux 拒绝（`klogctl: Permission denied`）；root 后可通过 `su -c dmesg` 读取。

## 6. disasm_sym 用法

```powershell
$tool = "D:\daima\root\ghostlock-app\tools\extract_rs\target\release\examples\disasm_sym.exe"
$img  = "D:\daima\tmpbuild\ota_work\ghostlock-payload-42328\boot.img"

& $tool --containing $img 0x10a1d1c 0xed750c

# 导出内核 Image（供其他工具使用）
```

## 7. 标准 runbook

1. 确认设备在线且 boot 完成：`adb devices`、`getprop sys.boot_completed`。
2. **等待系统稳定再跑**：`uptime > 5 分钟` 且 1 分钟负载 `< 10`（刚开机时厂商服务占满 CPU，此时运行 walk 崩溃率极高；实测 27 分钟系统空闲时首轮即过）。
3. 确认 offsets：`/data/local/tmp/offsets.json` 为当前内核条目（或按 §3 推送）。
4. 构建：`make NDK_ROOT=... ghostlock`。
5. 推送 + MD5 校验（防止半包）：见 §4。
6. observe 冒烟：`GHOSTLOCK_OBSERVE=1 GHOSTLOCK_ROUTE=mcast ...`，应看到 `errno=99` 且设备不重启。
7. live 运行：`GHOSTLOCK_ROUTE=mcast GHOSTLOCK_CORE=4 GHOSTLOCK_CONSUMER_CORE=5 ...`。
8. 验证：`su -c id` → `u:r:ksu:s0`；`/proc/modules` → `kernelsu ... Live`。
9. 留存日志：拉取 `.ghostlock_ksu.log`、保存运行输出。
10. **不要 kill 处于 sigsuspend 的 `ghostlock` 进程**：root 完成后它会挂起等待，属正常状态；`kill -9` 可能触发 CVE 残留状态的清理路径导致数分钟后延迟 panic（实测踩坑）。重启后进程自然消失。

### 7.1 KernelSU 版本配对（管理器 ↔ 驱动，2026-09-13 最终方案）

管理器与 `ksud`/内核驱动必须**同项目同版本**，否则管理器报"版本不匹配"或行为异常。本机最终采用**官方 KernelSU 成对**：

| 组件 | 来源 | 版本 |
|------|------|------|
| 管理器 APK | 已安装官方 KernelSU（`me.weishu.kernelsu`） | v3.3.0 / versionCode 32601 |
| ksud/驱动 | 从该 APK 提取 `lib/arm64-v8a/libksud.so` → `/data/local/tmp/ksud` | ksud 3.3.0 / 驱动 32601 |

- 提取：`unzip base.apk lib/arm64-v8a/libksud.so`；校验：`ksud -V` → `ksud 3.3.0 (uapi: 2)`，且内置 `android14-6.1_kernelsu.ko`、支持 `late-load --kmi --allow-shell`。
- **ReSukiSU 组合不可用（重要）**：ReSukiSU 管理器 v4.2.0-rc1（35061）在本机**一打开即内核卡死 → watchdog 重启**（实测复现；同驱动下官方管理器不卡死）。ReSukiSU 管理器已禁用；其 ksud 备份于 `/data/local/tmp/ksud_resukisu_35061`（如需可恢复）。
- 换驱动版本后需**重启并重新 root**（late-load 不持久）。

## 8. 已知坑

| 坑 | 现象 | 处理 |
|----|------|------|
| PowerShell UTF-16 重定向 | 日志文件乱码/读不出 | 用 `Tee-Object`，或按 UTF-16 读取 |
| stdout 块缓冲 | 进程存活时日志截断 | 拉设备侧日志文件；或给后续输出加 `log_sync` |
| 多设备 | 命令打到错误设备 | 一律 `-s <serial>` |
| 失败=重启 | panic 后设备重启、日志丢页缓存 | PC 端实时落盘；pstore 仅首启可读 |
| f2fs 回滚 | 日志偶尔丢行 | 关键阶段 `log_sync()`（PR#127 已引入） |
| adb shell 引号 | 环境变量传参失败 | 整体用双引号包裹 shell 命令，内部用单引号 |
| `su -c` 交互 | 组合命令挂起 | 分步执行；shell 流程已用 `--allow-shell` |
| 页面筛选 | W1 约半数页面因 `initialized` 字节为偶被拒 | 属预期（PR#127），重喷即可 |
| 开机后过早运行 | walk 崩溃重启 | 等 `uptime>5min`、`load<10` 再跑（见 §7） |
| kill parked ghostlock | 数分钟后延迟 panic | 保留进程；重启自然清理 |
| 投毒后打日志（开发者） | "walk 完成但写入无效"或 NULL 解引用 panic | 投毒→walk 之间 waiter 线程禁止任何 syscall：`pr_info`/`write`/`fsync` 都会冲掉栈上的伪造 waiter |
| 版本不匹配告警 | 管理器提示管理器/驱动版本不一致 | 按 §7.1 配对同版本；驱动版本随 ksud 走，换 ksud 后需重启重载 |
| 划掉/强停管理器或 ghostlock | 内核 panic 重启（KSU 清理路径） | 不要杀这两个进程；管理器刷新不显示 root 时直接重开界面即可，不划后台 |

## 9. 崩溃机理与重试策略（2026-09-13 实测）

### 9.1 崩溃现场分析

崩溃 dump（`ramoops_p11.txt`）寄存器：

```text
Unable to handle kernel NULL pointer dereference at 0x339
pc = rt_mutex_adjust_prio_chain+0x1ec      ; ldr x8, [x27, #0x38]
lr = rt_mutex_adjust_prio_chain+0x130      ; trylock 返回点（lock 有效）
x24 = 0xffffff81c7228000                    ; = 记录的 fake_lock 页基址（指针正确）
x27 = 0x0000000000000301                    ; = [page+0x10] 读出的 lock->waiters.rb_leftmost
```

`lock->waiters.rb_leftmost` 本应指向 `page+0x300`（payload 里的 `fake_w0`），实际读到垃圾值 `0x301` → 解引用 `0x301+0x38 = 0x339` 崩溃。

**结论：fake_lock 指向的页里不是我们的 payload —— skb 页回收竞争（reclaim）偶发失败。** 不是投毒几何问题，也不是管理器问题；W1/VR/W2 任一阶段的 walk 遇到坏页都会以同一签名崩溃。

### 9.2 成败分布与重试

- 同一二进制、同一参数下，单轮成功率约 **25–30%**（期望 3–4 次成功一次）。
- 实测批次：run 20（W1 崩）→ 21（W1 崩）→ 22（W2 崩）→ **23 成功**；此前 mcast14/16 也是一次成功。
- 崩溃即内核 panic → 自动重启 → 重新 root（late-load 不持久，重启本来就要重跑）。

### 9.3 自动重试脚本（PC 侧）

`D:\daima\tmpbuild\retry_root4.ps1`：等设备启动 + `uptime>240s` → 后台运行 GhostLock → 轮询 `/proc/modules` 是否出现 `kernelsu`；崩溃则等下一次启动继续，直至成功。

### 9.4 为什么不要杀管理器/ghostlock

两次实测（`kill -9` parked ghostlock、划掉 ReSukiSU 管理器）后数分钟内出现内核 panic 重启。KernelSU 的进程清理路径会触碰被利用污染的 rt_mutex 状态，杀进程可能触发该路径。管理器"没立刻显示 root"属于显示刷新问题，重开界面即可，**不要划掉后台**。
