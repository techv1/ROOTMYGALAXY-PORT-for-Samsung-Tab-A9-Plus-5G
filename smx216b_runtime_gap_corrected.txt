Resolution:
- Total SP decrement: 0x60 + 0x1b0 = 0x210 bytes (528 bytes).
- Frame Pointer (x29) is at offset +0x1b0 relative to the current bottom of stack.
- The stack waiter is allocated at:
  0xffffffc0103c0a64: sub x0, x29, #0xc8
- Exact coordinate relative to current SP:
  (SP + 0x1b0) - 0xc8 = SP + 0xe8 (232 bytes above current SP).
- Exact coordinate relative to caller's SP (SP_entry):
  SP_entry - 0x60 - 0xc8 = SP_entry - 0x128 (296 bytes below caller SP).

3. RE-EVALUATION OF FEASIBILITY STATEMENT
====================================================================================================
Evaluation:
Because dup_task_struct() explicitly executes `memset(stack, 0, 0x4000)` on newly allocated/cached
thread stacks, a newly spawned thread's stack CANNOT retain arbitrary pre-seeded waiter objects
from an earlier thread lifetime.
Instead, reclamation of the dangling waiter pointer at [SP_entry - 0x128] must be achieved via
in-thread deep syscall call stacks (e.g. nested filesystem, binder, or netlink calls) executing
within the SAME thread before task destruction, or by precisely overlapping a newly instantiated
frame before another unblock path dereferences pi_blocked_on.

Therefore, the claim of "runtime GhostLock feasibility" cannot be supported on static analysis alone.
The existing evidence supports strictly:
  "CVE + STATIC STACK-LAYOUT COMPATIBILITY"
Full runtime exploitability requires demonstrating a legitimate in-thread syscall stack overlap
or race window that survives RCU-delayed freeing and the explicit 16KB stack zeroing.
